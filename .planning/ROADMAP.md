# Roadmap: Finance Bot

## Overview

Путь от пустого репозитория до бота, которым пользуются каждый день. Сначала поднимаем бесплатный круглосуточный сервис на Oracle Cloud (HTTPS, CI/CD, бэкапы) и параллельно фиксируем реальное поведение iOS-автоматизации «Транзакция» на iPhone пользователя: от этого корпуса payload'ов зависят парсер сумм и идемпотентность. Затем идут регистрация по инвайтам, личные токены и изоляция данных. После этого ядро продукта: каждая оплата Apple Pay попадает в бот без дублей, и сразу виден остаток недельного лимита. Дальше бот получает кнопки управления тратами и обучаемую категоризацию, настраиваемый лимит с переносом, алертами и балансом, отчёты с диаграммами и автосводками. В конце проект готовится к приёму других пользователей и к показу рекрутерам: приватность и README-витрина.

## Phase Details

### Phase 1: Фундамент и разведка iOS-Команды
**Goal**: Сервис бесплатно и круглосуточно работает на Oracle Cloud по HTTPS, деплоится автоматически и бэкапится, а реальное поведение iOS-автоматизации «Транзакция» на iPhone пользователя зафиксировано в корпусе payload'ов
**Depends on**: Nothing (first phase)
**Requirements**: SPIKE-01, SPIKE-02, FND-01, FND-02, FND-03, FND-04, FND-05, FND-06, PRIV-03
**Success Criteria** (what must be TRUE):
  1. `https://<поддомен>.duckdns.org/health` отвечает 200 с Oracle Cloud Always Free VM; стек поднят через Docker Compose (app, migrator, postgres, caddy), и миграции применяются отдельным одноразовым шагом до старта приложения; аккаунт Oracle переведён на Pay As You Go (по документации проверено, что отбор простаивающих инстансов на него не распространяется), настроен бюджетный алерт
  2. Пуш в main запускает GitHub Actions: сборка, unit-, интеграционные (реальный PostgreSQL) и архитектурные тесты, проверка gitleaks, а при зелёном прогоне автоматический деплой на VM; в репозитории нет ни одного секрета
  3. Ежедневный шифрованный бэкап БД уходит во внешнее хранилище вне Oracle (Backblaze B2 или Cloudflare R2), и восстановление из него на чистую базу выполнено хотя бы один раз
  4. Реальные оплаты Apple Pay с iPhone пользователя (карты PKO BP, mBank, Millennium) доходят до сервера, и в репозитории лежит обезличенный корпус payload'ов с описанием формата суммы, даты и продавца; каждый пограничный случай из SPIKE-01 либо записан, либо помечен «не воспроизведён» с решением, как его обрабатывать; записано, как часто автоматизация срабатывает дважды на одну оплату
  5. Задокументировано, принимает ли шаблон Команды токен через «Вопросы при импорте» без вшитого секрета (проверено установкой по iCloud-ссылке), и как «Получить содержимое URL» ведёт себя при ответах 4xx/5xx
  6. Логи сервиса не содержат сумм, продавцов и токенов: это задано настройкой логирования с первого деплоя и проверяется автотестом

### Phase 2: Регистрация, доступ и Telegram-канал
**Goal**: Только приглашённые пользователи регистрируются в боте и получают личный токен для iOS-Команды, а данные каждого пользователя полностью изолированы
**Depends on**: Phase 1
**Requirements**: ACC-01, ACC-02, ACC-03, ACC-04, ACC-05, ACC-06, ACC-07
**Success Criteria** (what must be TRUE):
  1. В режиме `invite` (по умолчанию) `/start` без валидного кода не регистрирует пользователя, а с инвайт-кодом, созданным администратором, регистрирует; у кода есть лимит использований и срок действия, исчерпанный или просроченный код не регистрирует; в режиме `open` код не нужен
  2. Сразу после регистрации пользователь получает личный секретный токен, а в базе хранится только его хэш
  3. После `/token` пользователь получает новый токен; запрос к API со старым токеном сразу отклоняется, с новым проходит
  4. Автотесты изоляции подтверждают, что пользователь B ни через API, ни через подделанное нажатие кнопки не может прочитать или изменить данные пользователя A
  5. Бот не отвечает в группах и каналах; запрос на вебхук без верного секретного заголовка отклоняется; повторная доставка того же обновления Telegram не обрабатывается дважды

### Phase 3: Приём трат через Apple Pay и вручную
**Goal**: Каждая оплата Apple Pay автоматически и без дублей попадает в бот, наличные и BLIK вносятся одним сообщением, и после каждой траты пользователь видит остаток недельного лимита
**Depends on**: Phase 1, Phase 2 (корпус payload'ов из Phase 1 нужен для парсера и идемпотентности)
**Requirements**: ING-01, ING-02, ING-03, ING-04, ING-05, ING-06, ING-07, ING-08, ING-09, MAN-01, MAN-02, MAN-03, CAT-01
**Success Criteria** (what must be TRUE):
  1. Пользователь по ссылке из бота ставит готовую Команду, настраивает автоматизацию «Транзакция» по инструкции на русском, делает тестовую отправку и получает от бота подтверждение, что связка работает
  2. Оплата Apple Pay за несколько секунд приходит в бот подтверждением: сумма, продавец, категория, остаток недельного лимита из 200 zł; популярные польские продавцы (например, Żabka, Biedronka) сразу получают свою категорию
  3. Суммы из корпуса спайка (`1 234,56 zł`, неразрывные пробелы, меньше 1 zł и от 1000 zł) распознаются верно, исходная строка сохраняется; если банк не передал сумму, бот просит её ввести и трата не теряется; оплата не в PLN не записывается как злотые — бот просит сумму в PLN, и до ответа трата не идёт в лимит; при сбое Команда повторяет отправку 2–3 раза, и только если сервер так и не сохранил трату, на iPhone появляется уведомление «не сохранено»
  4. Повторная отправка той же транзакции (в том числе повторные попытки самой Команды) не создаёт дубль; почти одинаковая трата (та же сумма, продавец и карта в пределах ~2 мин) не теряется и явно помечается возможным дублем, а пользователь одной кнопкой исправляет решение бота («Это была отдельная покупка» или «Удалить дубль» — в зависимости от поведения по умолчанию, выбранного по данным спайка)
  5. Сообщения `45 такси`, `такси 45` и `320 куртка !` создают трату с таким же подтверждением; трата с `!` сохраняется вне лимита и не уменьшает остаток

**Notes**: Парсер сумм, нормализация продавцов и идемпотентность проектируются по корпусу из Phase 1, а не по догадкам. Рекомендуется `--research-phase`: поведение Команд описано только сообществом. ### Phase 4: Управление тратами и обучаемые категории
**Goal**: Пользователь исправляет любую трату прямо из подтверждения, а бот учится раскладывать траты по категориям на его выборе
**Depends on**: Phase 3
**Requirements**: MAN-04, MAN-05, MAN-06, CAT-02, CAT-03, CAT-04
**Success Criteria** (what must be TRUE):
  1. Под каждым подтверждением есть кнопки «сменить категорию», «Не в лимит» / «Вернуть в лимит», «изменить» и «удалить»; нажатие обновляет сообщение на месте вместе с остатком лимита и срабатывает только для владельца траты
  2. Пользователь меняет сумму или дату траты, и подтверждение с остатком лимита показывает новое значение
  3. Удалённую трату можно вернуть кнопкой отмены; сообщение обновляется на месте, без отдельного вопроса «вы уверены?»
  4. Нераспознанная трата сразу записывается в «Другое», и в том же сообщении бот предлагает категории кнопками; выбранная категория запоминается, и следующая трата у того же продавца сразу получает её
  5. `/other` показывает траты в «Другом», и пользователь может разобрать их позже

### Phase 5: Недельный лимит, алерты и баланс
**Goal**: Пользователь настраивает недельный лимит под себя, вовремя получает предупреждения и всегда видит корректные остаток лимита и баланс
**Depends on**: Phase 4
**Requirements**: LIM-01, LIM-02, LIM-03, LIM-04, LIM-05, LIM-06, BAL-01, BAL-02, BAL-03, BAL-04
**Success Criteria** (what must be TRUE):
  1. Пользователь меняет недельный лимит (по умолчанию 200 zł); неделя всегда пн–вс; изменение вступает в силу по зафиксированным правилам, а прошлые недели не переписываются
  2. В режиме переноса остаток или перерасход недели переходит на следующую без потолка и виден в подтверждении; в режиме «с нуля» каждая неделя начинается с полного лимита; накопленный перенос можно сбросить вручную
  3. Бот предупреждает о 80% и 100% лимита ровно по одному разу за неделю на каждый порог (скачок с 75% до 105% даёт алерт 100%); траты вне лимита не уменьшают остаток и не вызывают алертов, но учитываются отдельно
  4. Изменение или удаление старой траты корректно меняет остаток и перенос, потому что всё пересчитывается из истории; границы недели по Europe/Warsaw верны, в том числе в выходные перехода на летнее и зимнее время
  5. `/balance 3200` задаёт баланс, траты автоматически его уменьшают, `+5000 зп` увеличивает, и пользователь в любой момент может посмотреть текущий баланс

### Phase 6: Отчёты, диаграммы и автосводки
**Goal**: Пользователь видит, куда уходят деньги: отчёты за неделю и месяц с диаграммой, а итоги приходят сами по расписанию
**Depends on**: Phase 5
**Requirements**: REP-01, REP-02, REP-03, REP-04, HLTH-01
**Success Criteria** (what must be TRUE):
  1. `/week` показывает потрачено / лимит, остаток, разбивку по категориям и траты вне лимита отдельно
  2. `/month` показывает разбивку по категориям, итоги по неделям, сравнение с прошлым месяцем и траты вне лимита отдельно
  3. К отчётам прикладывается PNG-диаграмма распределения по категориям с корректной кириллицей, сгенерированная в продакшен-контейнере; если отрисовка не удалась, отчёт всё равно приходит текстом
  4. Сводка недели приходит в воскресенье вечером, сводка месяца приходит 1-го числа по времени пользователя, и каждая ровно один раз, даже если сервер перезапускался около момента отправки
  5. Если несколько дней подряд нет трат через Apple Pay (порог настраивается), бот один раз напоминает проверить автоматизацию и не повторяет напоминание, пока траты не возобновятся

### Phase 7: Приватность и публичный запуск
**Goal**: Бот готов к другим пользователям и к показу рекрутерам: хранимые данные прозрачны и удаляемы, логи чисты, репозиторий оформлен как витрина
**Depends on**: Phase 6
**Requirements**: PRIV-01, PRIV-02, PORT-01
**Success Criteria** (what must be TRUE):
  1. `/privacy` объясняет, какие данные хранятся и зачем
  2. `/deleteme` после подтверждения удаляет все данные пользователя (траты, правила, настройки, баланс, токен), и после этого его старый токен не принимается
  3. Автотест чистоты логов (PRIV-03, заведён в Phase 1) покрывает все сценарии, добавленные в фазах 2–6: приём трат, вебхук, ошибки
  4. Публичный README содержит схему архитектуры, ADR по ключевым решениям, инструкцию запуска, и GIF-демо на фейковых данных; публичного инвайт-кода в README нет
